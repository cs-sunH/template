# die/ — Codex Cloud 跨账号开发及交接规则

本文件适用于仓库 `die/` 子目录。两个 ChatGPT Plus 账号分别运行独立 Codex Cloud 任务；
**GitHub 上已合入共享分支的代码与 docs/HANDOFF.md 才是共享状态**。
请勿假设能够读取另一个账号的聊天记录、隐藏 Session 状态或尚未提交的文件。

## 每轮任务开始前（必须）

1. 阅读 `die/docs/PROJECT.md` 与 `die/docs/HANDOFF.md`。
2. 检查当前分支、`git status`、`git rev-parse HEAD`、近期提交与工作区改动。
3. 如工具/权限允许，核实 GitHub 共享集成分支上的最新 commit SHA；确认工作区包含上次**已合并**的交付版本。
4. 如果分支/版本不一致、存在无法解释的未提交修改，或不能确认上轮改动已进入共享分支，先报告并停止有风险的修改，不能强行覆盖或猜测状态。
5. 先依据 `HANDOFF.md` 的 Next Step 继续，不重复已完成并通过验证的工作。

## 实施范围和开发节奏

- 用户新增的建模原则（2026-10-14）：与硬件设计参数、软件任务输入参数不直接相关的辅助细节，能用简单数学公式直接计算时，采用公式，不进行深入建模。
- 复杂度须服务于可观察的参数响应、容量/工作量守恒或外部依赖与竞争。优先闭式、解析计数和固定数量的分段公式；新增状态或复杂数值机制须说明关联的输入/行为、简单公式不足的证据及运行成本。
- 该原则不能用来省略源架构变量、真实任务 shape/精度/TP/span、必要的就绪和共享资源约束，也不能通过额外延迟系数人为制造参数响应。

- 优先只修改 `die/`；其他目录如需变更，先说明必要性与风险。
- 读取真实代码再规划工作；不要猜测项目功能、入口、测试命令或用户意图。
- 把长任务分为小而完整、可以验证的阶段；每完成一个阶段尽可能形成可提交的成果。
- 遵守已有设计决策，并及时在 `PROJECT.md` 或 `HANDOFF.md` 记录新决策。
- 不允许两个独立 Session 同时修改同一套文件或向同一共享分支并行推送冲突内容。
- 不要提交 API Key、访问令牌、凭据、个人隐私、临时缓存或大型生成产物。

## 每轮结束/换账号前（必须）

1. 运行相关测试，忠实记录命令和结果；不能运行时说明原因，**不得声称未执行的测试已通过**。
2. 更新 `die/docs/HANDOFF.md`：Current Status、Completed、Next Step、Important Decisions、Files to Continue、Tests、Blocking Issues、Handoff Notes。
3. 清楚记录尚未完成的工作、关键判断以及接手方必须知道但难以从代码推出的信息。
4. 尽可能把代码改动和 HANDOFF.md 一起提交。允许操作时推送或创建 PR；无权限时，列出用户需要在 Codex Cloud / GitHub 界面完成的具体步骤。
5. **PR 未合并、推送失败、测试阻塞或远端版本未确认时，明确标记 NOT READY FOR HANDOFF**，不能宣称下个账号可直接接棒。
6. 最终答复包括：工作分支、提交 SHA（如有）、PR 链接和合并状态、测试结果、下一步。

## 交接判定

只有当上一轮成果进入 `PROJECT.md` 指定的共享集成分支，并且 `HANDOFF.md` 与代码一致时，
下一账号才应基于最新 GitHub 状态创建新 Cloud Task 接棒。

此协议只实现**代码与摘要状态接力**，不提供跨账号 Session 恢复，不检测额度，也不自动切换账号。
