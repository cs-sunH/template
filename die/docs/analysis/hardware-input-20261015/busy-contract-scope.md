# M80×128×4096 busy 条件界与合同范围

本说明只针对当前 M80×N128×K4096、单 Core、严格 FP32 的 OS Plan，不改 busy 定义或验收阈值，也不声称排除所有可能的累计曲线表示。

该 Plan 有 640 个相同 K 消费单位；每单位对应 131072 Vec eqops，解析 `C_in` 与 `COMPUTE_GATE` 工作进度同一比例，故当前 Plan 的最大消费率为 `c_max=1207.09228515625` 单位/s。输入 credit 容量 `B=2`，epoch 间实际 credit 首尾相接、无额外注入。若 HBM 正服务只有 `J` 个 on-runs，则最多 `J+1` 个无 load 区间各消费 `B` 单位；其余至少 `640-(J+1)B` 单位必须在正服务区间消费。即使 compute 可停顿或变速，仍有

```text
busy >= max(0, (640 - (J+1)*2) / 1207.09228515625)
```

`J=16` 时下界为 `0.502032866s`。参考 busy 为 `0.1314816s`，新合同的 20% 上限为 `0.15777792s`，所以该条件界下所有 `J<=16` 的曲线都超过20%。达到不再由此界强制超过20%约需 `J=224`：`J=223` 下界 `0.159059918s`，`J=224` 下界 `0.157403044s`。224个正服务区间至少需要 `2J-2=446` 次内部 on/off 转换（两端取正服务时的最小数）。根设计§1.5/§13与HANDOFF均要求曲线折点、活动边界和隐藏切换统一计入5/8/16描述预算；446次显然超预算。这里的 J 是实际服务运行数，不能从当前serialized描述数7推为 J≤7；预算合规需要实数曲线/运行时能证明其隐藏切换也已计数。

`c_max` 的适用边界是 `C_in` 的语义。当前 `Mapping.cc` 的 `append_os_service_curve` 以真实累计 K 单位生成 `C_in`，计算 activity 的 `COMPUTE_GATE` 工作量与输入消费进度同一斜率；`append` 使用的首 cohort 与剩余工作也都由真实 Geometry/Counter 事实得出。因此该值适用于当前 Plan，并且不因允许停顿而变大。总 FP32 工作守恒本身并不自动证明任意未来表示都必须按此斜率消费 credit：若某表示在 K 算术完成前就释放输入 credit，必须同时给出有界的在途输入槽/存储、对应本地工作和依赖凭据，并把其存活字节计入静态 SRAM 峰值或其他明确容量。当前 Plan 没有这种额外路径；全体输入约13.1MB，而单核 SRAM 为0.25MiB。不能把未记账的提前消费当成合法曲线来否定上述条件界。

这不是全局“所有有限曲线都不可能”的证明：若未来提供不同且可审计的物理存储/消费模型，应重算条件界。当前合同没有需要新用户裁定的歧义；busy 继续按10%目标、经记录合理校准后20%容许、超过20%失败报告。当前轴上的 busy 超过20%，如实标记 `failed`/`tradeoff_unresolved`，不自行放宽指标或减少隐藏切换计数。

依据：根设计§1.5、§1.6、§8.2.1、§13；`die/src/Mapping.cc` 的 `append_os_service_curve` 和 `seal_activity`；`work/analytical-curves/axis/diagnostics/m80_n128_k4096_busy_bound.json`。这是条件数学界，不是新精度证书。
