# Four-repository control-marker rollout audit

Read-only source audit prepared 2026-10-14. No simulator source or tests were changed, and no tests were run for this audit. The shared worktree is at `codex/die-lifecycle-online-20261014`, HEAD `037f87fa6c2e9a6a0e0c665598f7bcad0e41b87f`. The four target variants are directories in this single repository, not independently checked-out Git branches: `astra-sim-face`, `astra-sim-face-LRU`, `astra-sim-wscllm-LRU`, and `astra-sim-joint`. The reference `astra-sim-wscllm` tree is concurrently being updated by `online_e2e`; preserve that work.

The scalar marker is blocked in all four variants when `coarse_die_runtime` is enabled. Their `Workload::issue_die_comp()` recognizes `ControlMarker` before normal die-spec dispatch and calls `local_hbm_bandwidth_model->issue_compute(1, 1, wlhd)`. That reaches `LocalHbmBandwidthModel::issue_job()`, whose coarse-runtime branch rejects `JobKind::COMPUTE`/`COMP` with `coarse_die_v2 COMP traffic must be owned by a typed plan`. The coarse endpoint is therefore never submitted and the marker cannot complete through this path. The throw originates in the HBM model; exact event-loop fallout differs by variant, so rollout verification should assert the marker's actual completion and terminal count, not just that the endpoint call was made.

## Preserve each variant's HBM kinds and completion ownership

FACE's enum is `COMP, COMM_READ, COMM_WRITE, DIE_COMPUTE` (`LocalHbmBandwidthModel.hh:64`); it has no RESTORE or POOL job kinds, and its coarse bridge explicitly accepts only communication endpoints. Do not add FACE-LRU or WSCLLM-LRU's Pool logic to this tree.

FACE-LRU, WSCLLM-LRU, and JOINT share `COMPUTE, RESTORE, COMM_READ, COMM_WRITE, POOL_READ, POOL_WRITE, DIE_COMPUTE, KIND_COUNT` (their headers are at `LocalHbmBandwidthModel.hh:62`, `:60`, and `:79`). Their coarse bridge distinguishes `comm`, `restore`, and `pool` owners and read/write direction; completion sidebands are accumulated into distinct communication, restore, and Pool counters. Preserve those enum cases, counter dimensions, and emitted business metric keys while adding a marker kind. In particular, do not route a marker through RESTORE or collapse existing Pool traffic into a generic COMP/marker counter. If adding an enum member, append it before `KIND_COUNT` so current numeric job-kind identities do not shift.

FACE-LRU's Workload has `hbm_endpoint_joins_` state for multi-leg Pool endpoints; its destructor frees the remote and HBM Pool leg cookies and clears that table (`Workload.cc:238–264`). Its HBM-model destructor cancels coarse jobs without notification and frees the carrier, but does not abandon the Workload join. WSCLLM-LRU explicitly calls `local_hbm_bandwidth_model.reset()` while `hbm_endpoint_joins_` is alive (`Workload.cc:115–145`); model teardown calls `abandon_hbm_endpoint_join()` for coarse and legacy work (`LocalHbmBandwidthModel.cc:107–139`), then Workload checks for unresolved joins. That ordering and failure check are part of the Pool teardown contract.

FACE has a two-arrival `hbm_comm_join_` latch for network-plus-HBM communication completions (`Workload.cc:955, 992, 1193–1200, 1340–1361`). Its HBM model cancels coarse jobs and frees carriers in its destructor (`LocalHbmBandwidthModel.cc:97–122`); it does not have a Pool join table. JOINT uses `hbm_join_pending_` with a stored HBM cookie, `begin_hbm_join()` and `consume_hbm_join_event()` (`Workload.cc:1591–1640`) and has transfer-specific completion callbacks in `issue_job()` (`LocalHbmBandwidthModel.cc:516–579`). Its model teardown cancels and frees coarse carriers (`:102–129`); do not replace its callback/join semantics with another variant's `Workload::call` path.

JOINT has an additional virtual pipeline marker beyond the static node branch: `issue_pipeline_control_marker()` (`Workload.cc:1097–1173`) is invoked by `TileTransportAdapter.cc:171`; `RemoteReadExecutor.cc:3631` constructs such a ControlMarker view. The virtual path validates a 1-op/1-byte marker and a non-null `pipeline_sink`, initializes its cookie, then also calls `issue_compute(1, 1, completion_cookie)` at `Workload.cc:1160–1167` for the die backend. `Workload::call()` transfers a `pipeline_sink` cookie to that sink exactly once (`Workload.cc:1983–1991`). A JOINT rollout must route this path to the marker endpoint too and preserve sink handoff; testing only `issue_die_comp()` leaves an active coarse-runtime failure untested.

## Existing marker tests cover legacy latency only

All four `die_model_adapter_test.cc` files contain Case C with a marker expected at `issue_tick + 101`: FACE `:413–431`, FACE-LRU `:435–453`, WSCLLM-LRU `:430–448`, JOINT `:750–769`. These fixtures write `die-model-profile: mesh_die_v1` and `local-mem-latency: 100` (`die_model_adapter_test.cc:279–285`), not `coarse_die_v2`. They prove the legacy `(1 op, 1 byte)` fluid job still costs the old 100 ns latency plus one drain tick; they do not test the coarse scalar guard, endpoint delay, or coarse marker completion.

Keep these legacy assertions intact when the coarse profile is off. Add a distinct coarse-profile fixture for each affected dispatch path and assert successful terminal delivery exactly once, `initial_delay_ns == local-mem-latency`, expected served prefix/owner category, and snapshot replay. JOINT additionally needs virtual pipeline-marker coverage that proves the original `pipeline_sink` receives the cookie once. Preserve each repo's exception/fail-closed behavior in failure tests.

## Read-only Runtime progress and metric sampling

All five trees expose `CoarseDieRuntime::counters_at(now_ns) const` (`CoarseDieRuntime.hh:45` in the four targets; line 49 in base wscllm). It copies the mutable `coarse_die::Runtime`, advances only the copy, reads its counters, and adds plan-cache counters (`CoarseDieRuntime.cc:192–200` in the four targets). The sample has no external completion callbacks. `query_progress(handle) const` exists everywhere. Base wscllm alone also exposes `query_progress_at(handle, now_ns) const` (`CoarseDieRuntime.hh:42–45`, `.cc:227–237`); it copies/advances a private Runtime and reads the selected execution's exact progress. This is the existing pattern for live marker-prefix sampling; the four variants do not currently have this per-handle time-sampled API.

`export_snapshot(now_ns)` is non-const and mutates the live Runtime: after checking the active Sys tick it calls `runtime_.advance_to(now_ns)`, dispatches terminal callbacks, schedules the next event, then exports (`CoarseDieRuntime.cc:163–189` in the four targets; base lines 239–265). Do not use it for live prefix observation.

The four target `MetricCollector.cc` files do not call `counters_at()`; their local-HBM contention records take a pointer to `LocalHbmBandwidthModel` and read cached getters such as `hbm_busy_ns()`, `hbm_shared_ns()`, `compute_bytes_served()`, `restore_bytes_served()`, and Pool getters. Those getters are plain const field reads in `LocalHbmBandwidthModel.hh`; legacy `advance_to()` updates the cached counters. Coarse endpoints instead live in `CoarseDieRuntime`; the wrapper currently copies their classified totals into `coarse_*_served_` at terminal callback, which is too late for a live prefix. Add a read-only Runtime sample for live progress where needed while keeping existing records and keys.

Base wscllm `MetricCollector.cc` already samples `coarse_die_runtime->counters_at(sim_end_tick)` (`:1584–1587`) and emits the coarse runtime record, then also emits the established local-HBM record and legacy getters (`:1820–1869`). Treat this as additive precedent: preserve the existing FACE/Pool/restore business metrics and local-HBM records, and add sampled coarse progress alongside them. Avoid replacing a Pool/restore category with a new generic marker metric.

## Shared endpoint API and compatibility

The vendor `Execution.cc` files are byte-identical across all five trees and `die/src/Execution.cc` in this worktree: SHA-256 `c96a0555cb23c8c31ba5ab191aae275dbdaa65b7d17e15eb0249a9c35e9c2cb3`. Each vendor `RELEASE.json` advertises source digest `f4f31a61ff4d050c11e0c57ae7364b0d34fcd0d92e8fe82275cd9a48e215ee84`. The optional endpoint `initial_delay_ns` is therefore already supported by the shared public Runtime in each target; it is parsed as an exact unsigned integer (`Execution.cc:451–453`), assigned to `plan->launch_ns` (`:918–925`), and validated on snapshot import (`:2418`). A marker wrapper can pass `local_mem_latency` as `initial_delay_ns` without changing the endpoint API or vendor-specific source.

For old endpoint JSON that omits `initial_delay_ns`, the endpoint plan summary deliberately omits that key and launch remains zero (`Execution.cc:918–925`). This preserves the canonical summary and old default endpoint fingerprint. The current `endpoint_allocation_test.cc:26–27` asserts omission of the summary key; it does not contain a hard-coded pre-change golden fingerprint. The same public test also exercises an endpoint with `initial_delay_ns = 100`, delayed readiness and snapshot roundtrip (`:81–182`). That is portable to all four variants as a Runtime JSON contract, while marker-wrapper completion/callback tests remain repo-specific.

### Rollout sequence

1. Keep the four wrappers independent; preserve each `JobKind` enum and its HBM ownership/join behavior.
2. Add a distinct marker endpoint path with the existing `initial_delay_ns` field. Do not send it back through scalar `issue_compute()`.
3. Sample live progress via a const Runtime copy at the requested tick; do not call `export_snapshot()` to observe it.
4. Emit the new sampled result additively and retain communication, DIE, restore, Pool, legacy busy/shared, and issued-byte metrics as appropriate to that variant.
5. Extend tests beyond the existing legacy `+101 ns` cases. Cover the static marker in all four repositories and JOINT's virtual pipeline marker, including exactly-once completion and teardown/cancellation ownership.
