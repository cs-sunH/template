# LRU prospective workspace admission design

Date: 2026-10-14  
Scope: read-only scheduler/compiler/runtime audit plus the separately authorized manager-only follow-up. This note records the production wiring design and its blockers; it does not authorize turning required workspace admission on in the scheduler.

## Finding

The KV manager has one central fit gate (`SessionKVCacheManager.ensure_physical_fit`). Reservations, history restore/migration, and local prefill/decode growth all converge on it, so an immutable per-rank future-workspace floor can be added without changing whole-session LRU, remote-pool accounting, or the journal. The correct serialized-resource margin is `base + max(A, E)`, where `A` is the actual active COMP workspace reported by C++, and `E` is an immutable compiler-derived peak for any later legal COMP task on that rank. Do not add `E` to the snapshot or treat it as KV, reservation, active workspace, or remote bytes.

This manager floor is useful in isolation, but is not yet a production capacity certificate: the LRU graph emits `remote_store` as an unjoined side branch, so the manager frees a victim's local KV before the source-side store has released those bytes. A later KV allocation or die Plan can therefore overlap the still-live victim source bytes. `max(A,E)` protects compute workspace; it does not represent this transfer-tail residency. Required-mode activation remains blocked until source release is ordered before reuse or the physical-capacity protocol retains those bytes until source release.

## Scheduler and manager path

- `OnlineSchedulerBase.__init__` builds the die model context from the manifest/config (`online/online_scheduler_base.py:207-212,378-397`). The context is currently an emission carrier: its docs state that spans are installed per graph emission (`online/die_model_adapter.py:173-181,305-327`), and the exact `DieTaskSpec` is built later from the emission's op kind, spans, layer count, and weight passes (`die_model_adapter.py:348-384`). No policy-time envelope is queried.
- The LRU constructor calls `super()` and then creates topology and `SessionKVCacheManager` (`online/wsc_llm_online_scheduler.py:371-390,405-439`). This is the future place to install an already-computed floor; it must be computed from the complete manifest before `online_service.py` deletes that manifest (`online/online_service.py:197-199,277-298`). The service currently selects `workspace_admission` separately (`online_service.py:211`), but a prospective certificate is neither generated nor passed there.
- Schema-v2 workspace state is applied at the start of a decision batch before completions, arrivals, and policy (`online/online_scheduler_base.py:399-429; online/wsc_llm_online_scheduler.py:554-569`). The manager gets a full-rank absolute view through `set_external_workspace_view`; after policy, the response includes `workspace_capacity_snapshot`. Thus, manager E must be fixed at construction and remain outside the existing revision/active-byte maps.
- Policy admission is the right fit hook. `_try_admit_prefill` first reserves final Decode KV (including net-credit retry), then plans history restore/migration, extends reservation after history migration, and grows Prefill KV (`online/wsc_llm_online_scheduler.py:1430-1625`). `_try_admit_waiting_decodes` releases that reservation, moves Prefill KV to Decode, then grows Decode KV (`1644-1744`). `reserve_request_capacity`, `extend_request_capacity`, history operations, and `_grow` all use the manager's `ensure_physical_fit` (`session_kv_manager.py:2508-2679,2685+,3010-3251`).
- P emits one complete request body while its instance is busy; D emits one frozen active-decode train while busy (`online/wsc_llm_online_scheduler.py:1383-1428`). A train's membership and exact `pass_spans` are formed from the currently active Decode set only at train creation (`833-889`), so future membership is not known at an earlier admission decision.

## Why `max(A,E)` is valid only for the normal serial path

For the production path, the serial premise is supported by three independent facts:

1. Each per-rank graph builder chains each newly emitted main-chain node from `previous_id` (`online/graph_batch_builder.py:140-203`). Prefill is emitted as a complete body for a P instance and the instance is marked busy; Decode freezes and emits one train and remains busy until its completion (`wsc_llm_online_scheduler.py:1398-1428`).
2. `Workload::issue_dep_free_nodes` checks `hw_resource->is_available(nv)` before every issue (`astra-sim/workload/Workload.cc:399-419`). For `GpuComp`, availability is `num_in_flight_gpu_comp_ops == 0` (`HardwareResource.cc:236-237`). A completed coarse Plan releases its workspace lease before terminalization and the deferred issue retry (`DieModelAdapter.cc:163-168`).
3. C++ `WorkspaceAdmission::try_acquire` still accounts for actual concurrency as `active_workspace_bytes + candidate_workspace_bytes` (`astra-sim/workload/WorkspaceAdmission.hh:175-184`). It is the live authority for an actual Plan candidate; E is only a conservative KV-admission floor for a *future serialized* candidate.

There is an important boundary: `HardwareResource::occupy_class` for `GpuComp` only increments a count; unlike its HBM-DMA/CPU/GPU-comm branches, it has no fatal pre-increment check (`HardwareResource.cc:159-164`). The file explicitly says concurrent COMP occupancy is representable and production serialization comes from the availability gate. Therefore the certificate applies to the ordinary production graph + `Workload::issue_dep_free_nodes` path, not arbitrary/direct test-created concurrent COMP submissions or callers that bypass the gate. Any future route that permits simultaneous same-rank COMP Plans must continue to rely on C++'s exact sum admission and cannot use manager `max(A,E)` as a claim that concurrent workspaces fit.

Under those assumptions, `base + max(A,E)` reserves enough for the larger of the Plan already active on the serial rank and any future legal candidate. `base + A + E` double counts mutually exclusive compute phases. Conversely, it is unsafe if a same-rank future candidate can overlap the active Plan, or if E fails to bound a legal emitted candidate.

## Compiler-envelope coverage required before scheduler activation

The canonical C++ envelope query compiles one normalized `DieTaskSpec` and returns the max exact workspace over every mapping candidate for that one spec. It does not return a global max across op kinds or task shapes. The scheduler-side certificate must therefore query every legal task-spec shape and take the max per rank; it must not infer the global maximum from selected plans or a single largest-looking input.

The adapter already owns the operation mapping and schema construction (`online/die_model_adapter.py:348-384,387+`); task specs contain the local TP slice, spans, layer count, weight passes, and fusion policy. Use that path plus the real C ABI query. Do not reimplement the C++ workspace formulas in Python.

For a finite manifest, the prefill side is directly enumerable: for each request, use its actual history/context, prefill length, configured chunk size, P group, and each local TP rank; `_emit_prefill_stage` constructs spans as `(chunk, initial_context + processed + chunk)` (`generate_wsc_llm_trace.py:624-687`). Manifest rows already encode finite history/prefill/decode lengths (`plan_materializer.py:314-359`). Query each legal emitted op kind/region and take the per-rank maximum.

Decode is harder. A live Decode train contains all members currently in `active_decode`; each member contributes spans through `min(remaining, iterations)`, and iterations are the maximum remaining length, clipped by `SH_TRAIN_MAX_ITER` (`wsc_llm_online_scheduler.py:833-889`). Exact future membership depends on arrivals, queue/admission order, joins, completion timing, and capacity. A finite conservative query can use a manifest-derived superset of all possible Decode members on each statically routed D instance, maximum legal context and remaining Decode length, and the maximum legal train iterations (configured cap, or finite max manifest decode length when cap is zero). It may overestimate; that is safe if the C++ compiler's workspace assignment is monotone for all relevant causal/span/count/batch/layer dimensions. The C++ mapping proof must explicitly cover that monotonicity for every op family being admitted. If monotonicity or a finite task-shape bound is unavailable, exact enumeration of all legal subsets/batches can be exponential, and the scheduler must remain fail-closed rather than install a partial floor.

`die_model_oracle` is still absent from this LRU online package: `test_die_model_adapter.py:320-327` has a designed skip when its import fails. The currently present `die_workspace_envelope.py` / `test_die_workspace_envelope.py` provide an untracked C-ABI client/test in this checkout, but they are not wired into `DieModelContext`, policy construction, or `SessionKVCacheManager`. They solve only the low-level per-spec query, not task-shape coverage or future Decode membership. The exact bridge plan is: build the finite manifest certificate from canonical adapter specs plus the C ABI before manager construction; install the rank-complete E map once; then leave schema-v2 A revisions and C++ live lease admission unchanged.

## Remote-store and migration source-release blocker

Manager eviction immediately releases the victim's local KV and moves it to `REMOTE_MEMORY` (`session_kv_manager.py:1931-2008`). Graph emission deliberately forks remote stores as side branches and does not join them to the rank main chain (`online/graph_batch_builder.py:762-774`). It records edge `mem_store` IDs only to enforce same-session store-before-restore (`797-835`); it does not order all local reuse after source-side release.

The generator defines remote-store source release as `mem_store_completion` when the source is the edge rank and `remote_store_ack_recv` otherwise (`generate_wsc_llm_trace.py:1042-1062,1064-1127`). The non-edge path sends the victim bytes, writes the remote pool, then sends an ACK back to the source; the bytes remain live on the source through the source ACK receive. The generator also documents that `noc_migrate` keeps source bytes until `noc_migration_ack_recv` (`generate_wsc_llm_trace.py:864-867,931-1015`). Neither source-release node is joined to all later capacity reuse: remote-store tails are tracked only by edge `mem_store` IDs for same-session restore (`graph_batch_builder.py:797-835`), while the migration record exposes only a dependency-name string and destination-arrival node (`generate_wsc_llm_trace.py:1002-1015`).

Meanwhile a new `prepare_history`/restore or prefill can proceed on the manager's freed capacity, and a Decode rank can already have a different active session. The same-session restore tail only protects pool ordering, not capacity reuse. A compiler E query is not a bound for these outstanding source KV bytes. The capacity fix must cover *every* transfer that removes local manager residency while source bytes remain live, at minimum `remote_store` and cross-instance `noc_migrate`.

Minimum safe follow-up is to track per-source-rank release tails separately from the existing edge pool-write tails, capturing source ACK receive for non-edge store/migration and source `mem_store` completion for direct-edge store. Gate the first operation that reuses that source capacity after the relevant release node. If a restore or migration writes the destination before compute, its write must be ordered before reuse; gating only the first COMP is too late. An alternative is to retain released bytes as an explicit capacity hold until source release, but that requires a bridge/manager protocol change outside this manager-only task. Tests should exercise direct-edge/non-edge stores, cross-instance migration, repeated releases, next KV restore/write, next COMP, and ensure no deadlock/cycle with the triggering gate.

## Authorized manager-only floor change

Add an optional constructor keyword with a complete `rank -> exact uint64 bytes` mapping, default zero for legacy behavior. Copy and freeze it after rank state creation; validate exact rank coverage and each E against `capacity_bytes - model_weight_bytes`. Keep it out of journal rollback snapshots and keep all workspace snapshots/revisions describing only actual A.

At KV fit time use `max(actual_A, E)` in `_fit_remaining`, the impossible-after-reclamation arithmetic, and the LRU loop's fit condition. Preserve the existing bare-KV vs workspace-only check so workspace-only blocks do not evict cold candidates, debit remote pool, or increment deep-gap counters. Before reclamation, distinguish a request that cannot fit even in an empty instance after permanent E from temporary active A: reject the former with a specific `ValueError` (no epoch can change E); report the latter as `blocked_by_workspace=True` and leave all accounting unchanged. A released active A or a future decision event can retry the temporary case. `set_external_workspace_view` must continue validating actual `base + A`; E is not an actual physical lease and must not be added there.

Focused manager tests should cover: exact full-rank/u64 input and rejection without partial install; E immutability across journal rollback; exact `max(A,E)` behavior for A<E and A>E; E-only empty-instance overflow vs temporary A blocking; workspace-only blocks preserving a cold victim/remote pool until retry; continued whole-session LRU order and protected victims; blocked remote restore with no remote debit, then one restore after release; and reservation net-credit swap/rollback under the new floor. Use real existing focused/unit runner dependencies; do not stub or monkeypatch protobuf.

## Activation and acceptance gate

No scheduler required-mode activation until all of these hold:

- the C++ envelope certificate covers every emitted op kind and every legal finite-manifest task shape per rank, with a reviewed monotonicity argument and overflow-safe exact u64 result;
- actual selected/emitted Plans in real P/D fixtures are each `<= E`, including multi-request Decode trains, longer causal context, capped and uncapped iterations, all rank-local TP slices, and fused/materialized op regions;
- the production serial COMP and lease-release premise is preserved; C++ continues summing concurrently active leases where concurrency is possible;
- remote-store source-release tails (or explicit physical capacity holds) prevent local KV reuse while source victim bytes remain live;
- retry behavior remains event driven: blocked transient A waits for a capacity revision/completion, with no self-retry spin; impossible permanent E requests fail explicitly instead of leaving a dead epoch.

## Manager-only implementation status

The separately authorized follow-up is implemented in `session_kv_manager.py` and `test_workspace_admission_manager.py` only. The constructor accepts a full-rank exact-u64 `prospective_workspace_bytes_by_rank` mapping, validates each floor against empty HBM after model weights, defensively copies it into a read-only mapping, and defaults to zero. `_fit_remaining`, reclamation feasibility, and reservation extension use `max(A,E)`; actual workspace revisions/snapshot fields and journal rollback remain unchanged. A request impossible under permanent E raises before remote-pool or LRU mutation, while larger transient A returns a workspace block. The focused tests cover full-rank/uint64 validation, A/E boundaries, protected LRU ordering, retry/reclamation, restore pool preservation, reservation net-credit swap, extension failure atomicity, and journal rollback.

Validation results and identities are recorded in `README.md` and the sibling logs. No scheduler or bridge code installs the floor; the C++ compiler envelope coverage and transfer source-release blockers above still prevent production activation.
