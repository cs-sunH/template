## 可直接复用的生产几何和事实

已实现的三个头文件是数据来源，不需要再发明计数器或 geometry：

- `die/src/GemmOSGeometry.hh`：`GemmOSGeometry` 以整除/区间计数表示 OS 的 `R*Tk`；固定最多 32 个 M/N/K `AccessClass`（当前一核 FP32 E5 fixture 实际使用更少）。可复用 `output_fact(q)`、`wave_fact(q,k)`、`wave_slot_fact(global_wave,lane)`、`same_shape_run_end(q)`、`class_output_count_in_range()`、`class_consumption_count_in_cohort()`、`wave_ledger()`。`WholeRowClasswordFact`（`:82-95`）和 `whole_row_classword(m_tile)`（`:340-365`）给出行 q 范围、full-N 数、N-tail 及 full-M/M-tail 边界；这些是 O(1) 算术边界，不是逐输出 tile 列表。K 的 first/middle/final/tail 事实在 `AccessClass` / `WaveFact` 中。
- `die/src/GemmOSAccessCounter.hh`：`gemm_os_access_counter::count(Input)` 给一个真实尺寸、首/尾K标记的消费生成现有 dtype/path/dataflow 的整数及 `EqWork` 账本，不含生命周期、槽预约或 timing（文件头注释及 `:44-60`）。
- `die/src/GemmOSResourceFacts.hh` / 对应实现：`gemm_os_single_core_resource_facts(Hardware, Input)` 复用现有 Resource/Flow builder 产生 Load/Compute/Store 三个 13 域 `Activity`；非final K 的 Store 是空活动。它不附加 buffer credit，并明确拒绝未经证明的 multi-Core cohort 语义（`:9-17`）。

这些事实与旧建议 `die/docs/analysis/k-readiness-20261015/k-readiness-proposal-original.md` 的有限 shape/K 类方向一致。旧建议是 proposal，不是生产描述符/API。

## E5 和当前诊断边界

`die/docs/analysis/os-kernel-e5-granularity-audit-20261014.md`、`die/docs/evidence/gemm-axis-20261014/README.md` 已证实生产 E5 把 `R` output rounds 当 progress repeat，而非 `R*Tk` 离散 K readiness。E5 账本有精确整数守恒，但 finish/HBM-busy/shared-busy 仍不达 3%/5%；K4096 与 K4097 使用同 OS 16×64×64，K128 选择 WR，不能作深K OS 对照。`die/docs/analysis/k-readiness-20261015/k-readiness-proposal-original.md` 提的固定类/槽/稳定段只是旧方案建议，不是已验证实现。

`die/docs/evidence/k-readiness-20261015/raw/probe.cc` 复用 real facts + public Runtime，单/同步/50ms异步 phase 有诊断结果，但按文件自己的输出声明是 `complexity=uncompressed O(events)`（没有生产有界性声明）。它将同一 `Runtime` 用于每个 K stage 单活动 Plan，几何 token 负责就绪；事实活动明确要求 `credit_delta == {0,0}`，所以 public LP 的 13 域 work、owner Q/alpha 和 `private_time_s` 仍在，但 production Plan 的 signed-credit boundary rows没有进入该 probe。它既没有 cycle detector，也不能证明 O(1) 描述或repeat-count预算。

## 重要 readiness 审计：oracle 和当前 probe 都多 gate 了 Compute

`die/validation/compiled_gemm_oracle.py:452-472` 计算 output occupancy 时正确地只把 `active_compute` 在 final-K 时计作 output（`:455-458`），但启动条件在 `:466-472` 对**所有** Compute 都要求 `output_occupancy < 2`。因此两 output slots 满时，即便 loaded token 是该输出的 nonfinal-K，这个独立 oracle 也不让它启动。`die/docs/evidence/k-readiness-20261015/raw/probe.cc` 用同型条件：先算 `output_used = outputs + store + active-final-compute`，再用 `if(!compute && inputs && output_used<2)` gate 任意 K。两者可能共享了同一保守 backpressure 假设，若测试期间输出槽满且下一 ready K 为非final，就不能互相作为这条规则的独立验证。

现有真实 lifecycle driver采取 final-only reserve：`die/tests/os_lifecycle_runtime_driver.cc:582-603` 先找 token，只有 `final_k` 才 `first_free_output_slot()`、否则继续 Compute；终结时 final Compute 才转 Ready（`:711-717`）。真正的单 owner 13-domain exact scratch也一样：`die/docs/analysis/os-solo-13-20261014/stops/solo_stop_13.py:372-380` 允许 `not final` 在 `out==2` 时启动，final必须 `out<2`；`current/study.py:272-308` 注入“输出满+非final可启动、final仍等待”的转移检查。注意注入 fixture 不是完整 multi-K schedule 的可达性证明；同证据 README称实际完整 multi-K Runtime traces最多观测 output occupancy 1，只有 K=1 pressure fixture观测到2。因此目前可确认oracle gate定义过严；尚不能由已存 trace断言它改变了 E5 数值。

真实 SRAM约束是容量，不是这个过门条件：设计文档 `die内仿真器设计文档_最粗粒度参数响应版.md:320-331,355-372,598-600` 要求 `peak_live_buffer_bytes_per_core <= rho_sram*S_core`，OS同时计两个输入槽、FP32累加/partial、等待写回output buffers；K顺序消费并只在最后K产生外存写回。生产 mapping `die/src/Mapping.cc:1017-1022` 将 `accum` 单独计入，再将 `2 * output_tile_bytes` 明确作为 pending output slots，和双输入相加作静态 `sram_peak` 过滤。这支持“只在 final Compute reserve pending-output slot，Store终结才释放”；并没有把 output-queue occupancy作为非final Compute readiness依赖。产线 code/文档需以容量公式和 final-write lifetime为准，不能把静态 SRAM 两个 pending buffers等同于每个 nonfinal Compute需要一个空 buffer。

## 事件与 pivot 预算语义（不可混淆）

- 生产 `die/src/Execution.cc:28,1614-1704` 的 `kMaxAdvanceEvents=1,000,000` 是 `Runtime::advance_to()` **单次调用**内部事件循环的实际展开次数上限：只有走完整内部 deadline interval并 `integrate(next_delta)` 才增加本次 `events` 和累计诊断 `internal_events_`。到目标时间前没有内部事件的最后一段只 integrate 到 target，不计一次内部事件。它不是执行生命周期/多个 advance calls共享的1e6累计限额。
- `die/src/Execution.cc:1268-1287,1411-1465` 的 simplex `pivot_count` 在一次 `allocate()` 开头置零，被该次 allocation中的 tier solve 和 degeneracy fallback solve共享；超过256会 numerical_failure。每次 stage/event重新分配开始新budget。因此它不是256 events、也不是“整次 Runtime lifetime 只允许256 pivots”。
- Standalone estimate另有 `drive_submitted_standalone_estimate()` 的 lifetime `event_guard`（`:2649-2663`），每次 next_event/advance loop + `advance_to` 增一；其下游 advance_to仍有自己的单调用 guard。
- 当前生产没有“快进后补算的逻辑事件数”字段/抽象；`internal_events_`表示实际执行的区间数。已有 scratch 256 cap 通常专指“expanded discovery/transition events”，且 skip 次数另记 `skipped_waves/outputs`。若采用压缩，按周期乘数要分开保存逻辑完成/类别计数与实际探测/展开次数，明确实际 guard怎样作用；不能把实际 guard说成累计logical event budget或任意每周期重置。`compiled_gemm_oracle.py:429-431,479-484,561-564` 是另一个口径：其 1e6 `max_events` 计 arrival 和每次 stage completion，非内部LP pivot/interval循环预算。

## 给后续复用的约束

现有证据最有用的交集是：有限 geometry/per-K facts + row-major classword + 真实 L/C/S 槽转移 + 在稳定状态/LP region返回之后按周期增量累计时间和 union/busy/work。单owner exact identity结果支持 bounded tails和外停切段；异步owner证据目前只是若干简化或固定phase。生产验收需要新的联合owner phase/活动队列/槽/实际QalphaLP区域（含13域、private limit和生产credit若所选活动使用它）的可证稳定证据；arrival/cancel/capacity作为硬边界。当前源码对 production 1e6/256预算各有既定局部作用域，不应由研究 scratch的global expanded cap改写。历史 GMP/Fraction结果仅作公式和证明手法参考，不直接移植。
