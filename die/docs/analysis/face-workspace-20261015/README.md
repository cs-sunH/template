# FACE/FACE-LRU workspace admission and real Online delivery

The two FACE variants retain their distinct admission, KV retention, eviction, reservation and remote-pool policies. The coarse route uses the shared canonical Compiler/Runtime. It prepares an immutable Plan, obtains its exact workspace peak from the canonical accessor, acquires a rank-local token, and preflights raw task/Plan/hardware/bytes/ledger owner before graph take, GPU occupation or issue statistics. The parser's schema-1 diagnostic object may coexist with its original raw task; its presence must not reject a supported coarse task. JOINT has a separate intentionally stricter new-task wire boundary.

WorkspaceAdmission owns transient Plan tokens only. Python remains authoritative for model weights, resident KV and request reservations. Coarse Online automatically requires the versioned bridge; the legacy path retains v1. Every v2 request carries a complete sorted absolute rank view (revision and active bytes), every response returns a complete capacity split echoing each revision, and the ACK uses the same schema and delivery/batch identity. Missing, stale, noninteger, overflowing or mismatched fields fail before capacity installation. GraphBatch preflight checks every rank before installing any snapshot; issue retries cover the union of graph-touched ranks and ranks with a changed capacity split.

The manager validates the complete external workspace view atomically, subtracts it for physical fit and policy prefilters, and advances the existing capacity epochs for affected instances. Existing HBM used/remaining snapshots stay KV-only. Workspace bytes are neither fabricated KV nor remote-pool debits. Completion releases the actual token before terminal publication; cancellation preserves served work, emits Skipped and releases once. A blocked Plan stays free and does not occupy GPU or acquire a lease. The original one-GPU-COMP gate per rank is preserved.

The legitimate coarse configuration resolver intentionally has no legacy peak scalar. FACE's loader now obtains positive selector units from its already-resolved typed library summary (INT4 ops/s to the legacy selector's tera-unit field and the two HBM row peaks to GB/s), using the same conversion as the runtime oracle consumer. It does not insert a legacy scalar into the coarse system config or introduce a Python model. FACE-LRU gains the existing FACE thin coarse C ABI route. The selector still combines its existing local components and fixed D2D addend; coarse final stats disclose representative rank, absent collectives/queue delay and the approximate composition profile.

Reproduction uses isolated exact source stages, real repository protobuf schemas generated with protoc, actual two ABI libraries and the ordinary FACE config loader/plan materializer. Queue, manifest, model, rank topology, runtime configs and provenance sidecar are one matching input set. Selected failed loader/ACK/test observations are retained separately from final successful measurements, with per-run source and binary identity.

Open scope: future workspace margin remains E=0 in these FACE variants. A completed tiny run does not prove closed-input capacity extremes. KV could consume the space needed by a later positive-workspace Plan; admission needs a proven canonical future bound or a true pre-mutation proposal contract. Current active-byte handoff and prospective margin are different requirements. Further overlap cases, source-buffer release under migration/store, pressure/restore, complete GQA producer coverage, host-budget acceptance and target held-out accuracy must be reported only when actually measured. E5 remains failed, TX8 priors are frozen, and full production JOINT live-world import remains guarded.


Final measurements use source base `ca604f5` plus the recorded FACE changes. Each C++ selection passed 8/8, and exact staged Python passed 120/120 and 118/118 with actual ABIs and no skips. The four one-request baselines completed 3 deliveries/ACKs and 186 successful terminals each. Both two-request overlap runs completed 6/6 and 378 successful terminals; at tick 150000 ranks 20,21,26,27,32,33 held 16384 B each, while the original prefill was still running. Native tracing placed its FFN issue/finish at 122710/238744 ns. The final LRU mailbox assertions were a later test-only source change; measured Online production source and binaries are unchanged. See the adjacent evidence package for exact identities, raw logs and selected failures.

The physical source-release gap needs explicit follow-up. FACE-LRU's store ACK nodes and store→restore pool tails do not provide the WS-LRU capacity-consumer hook. Its manager frees logical KV when selecting transfer, before physical completion. NOC migration has the same source-capacity ordering concern. A future fit margin alone will not establish source-buffer safety; implement and test that separate ordering before claiming pressure acceptance.

## Reproduction

Use CMake, a C++17 compiler, Python and real protoc available in the environment. The measured toolchain was CMake3.31.10/GCC14.2/protoc3.21.12/Python protobuf6.33.5. `/workspace/cloud-setup/activate.sh` is the session's tooling, not a portable dependency.

Always pass `ASTRA_SIM_ROOT` to the aggregate (its measured default path is historical). Configure separate Release build trees for `astra-sim-face` and `astra-sim-face-LRU`, with `NETWORK_BACKEND_BUILD_AS_LIBRARY=ON` and `BUILDTARGET=congestion_aware`. Build `AstraSim_Analytical_Congestion_Aware_Online`, `die_model_cabi`, `coarse_die_cabi` and the eight `AstraSim_Analytical_Congestion_Aware_{DecisionMailbox,WorkspaceAdmission,BridgeLoopback,GraphBatchCommitter,ParsedBatch,DieModelAdapter,DieExecutionLifecycle,LocalHbmDieMemory}Test` targets. The measured exact commands and aggregate/cache identities are in `../../evidence/face-workspace-20261015/cpp/`.

`run_python_checks.py` accepts variant, isolated `--work-dir`, absolute `--legacy-library`/`--coarse-library` and unittest module names. The measured modules are `online.test_workspace_capacity_manager online.test_workspace_bridge online.test_die_model_adapter online.test_admission_liveness online.test_graph_batch_builder online.test_first_token_split online.test_train_machinery test_die_model_oracle test_face_scheduler test_face_kv_incremental_invariants`. It stages exact source and real protobuf output, and records its own identities.

Copy both files from `online-reproduction/` into an isolated directory under repository `work/` before executing them; they intentionally put generated inputs/stages/runs beside themselves. Do not run them in this tracked analysis directory. Then run from repository root:

```bash
bash work/face-workspace-repro/run_tiny_online.sh face legacy "$PWD/work/face-build/bin/AstraSim_Analytical_Congestion_Aware_Online"
bash work/face-workspace-repro/run_tiny_online.sh face coarse "$PWD/work/face-build/bin/AstraSim_Analytical_Congestion_Aware_Online"
FACE_TRACE_ENABLED=1 bash work/face-workspace-repro/run_tiny_online.sh face coarse "$PWD/work/face-build/bin/AstraSim_Analytical_Congestion_Aware_Online" workspace-overlap 150000
```

Repeat with `face-lru` and its independent binary. Build both ABIs in each build's `lib/`, or pass their actual paths through `DIE_MODEL_CABI_PATH`/`DIE_COARSE_CABI_PATH`; do not rely on the historical fallback directories. LRU uses its materializer-generated remote-memory config. The scripts generate matching queue/manifest/runtime inputs, canonical sidecars, real protobuf, source/binary identities and fresh run directories. A rebuild must record its new hashes rather than relabel the measured binaries. The six measured commands and run paths are in the evidence's `online/evidence/final-online-run-audit.md`.
