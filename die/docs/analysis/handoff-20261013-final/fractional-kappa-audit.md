# Fractional κ / Vec eqops path audit

Read-only audit of current `die/` source. No tracked files changed.

## Current path and blockers

- `Mapping.cc` computes `Flow::vec` / `Metrics::vecops` with integer `u128` (`Mapping.cc:~790-805`, GEMM; FFN similarly around `2082-2107`). Each κ is cast to `u64` before multiplication, so non-integral coefficients are truncated. `seal_activity` then narrows again through `as_u64(f.vec, ...)` into `Activity::vec_eqops` (`Mapping.cc:626`). `Activity` and Plan summary counters are `uint64_t` (`include/coarse_die/Plan.hh:20`; summary uses `as_u64` near `Mapping.cc:893`). This is the precision-loss seam; changing only compute-time coefficients would break the ledger/budget agreement.
- Plan v2 JSON writes `activity.vec_eqops` as an integer (`Plan.cc:174-185`). Import uses `require_u64` (`Plan.cc:341`), and `plan_to_json` hashes canonical `payload.dump()`; import recomputes that hash (`Plan.cc` around `plan_to_json` / `plan_from_json`). Integer-valued serialization therefore participates in existing fingerprints. Existing integer plans can remain byte-for-byte canonical if integral values continue to serialize as `uint64`.
- Runtime copies the plan's planned eqops into `long double` served counters and apportions them continuously by progress (`Execution.cc:924-927, 1360-1367`). Progress/counter JSON exposes numeric `vec_eqops` plus exact-decimal companions (`Execution.cc:1649-1652, 1684-1687, 1770-1773`). Snapshot v3 serializes served totals as decimal strings and parses them back to `long double` (`Execution.cc:1835-1836, 1857-1858, 2020-2021, 2130-2134`). The runtime accumulation path already accepts fractional planned totals once `Activity` can carry them.
- The fixed-layout public C ABI v2 structs declare `DieActivityV2.vec_eqops` and `DieCompletionV2.vec_eqops_served` as `uint64_t` (`include/coarse_die/Capi.h:~19,27`). They cannot encode fractions. Current exported C ABI functions mostly carry JSON (`Capi.cc` compile/estimate/progress/counters/snapshot functions); the struct fields have no current source consumers in this library. Do not change these v2 layouts or silently ceil/truncate into them. A future caller using a fixed v2 struct must either reject fractional eqops or use a new versioned struct/API.

## Minimal compatible direction

1. Make equivalent-op work a fractional scalar through the accounting path: change `Flow::vec`, `Metrics::vecops`, and `Activity::vec_eqops` from integer-only storage to a finite nonnegative floating work scalar; accumulate κ-weighted terms without integer casts. Keep every byte/element/physical-op counter integral. Use the same fractional κ coefficients in both the Vec ledger and GEMM tail budget, and charge strict-FP32 output-to-INT4 with `κ_quant` in both places. Source-operation counters can remain integers where they represent actual source operations; `vec_equivalent_ops` is a different, weighted cost quantity.
2. Preserve existing plan v2 integer compatibility by making serialization type-sensitive: if eqops is exactly integral and within `uint64_t`, emit a JSON unsigned integer; otherwise emit a finite JSON floating number. Import should accept old nonnegative integer values unchanged and finite nonnegative fractional numbers. Reject NaN/Inf, negative values, and values outside the representable/runtime domain. Keep byte fields on strict integer parsing. Keep the plan schema name v2 for additive numeric representation only if all current v2 consumers treat eqops as JSON number; otherwise retain an integer legacy field and introduce an explicit fractional sidecar/versioned schema. The latter is safer for clients with integer-only decoders but requires updating strict-key validation and canonical hash rules.
3. To retain default integer plan fingerprints, the canonical writer must continue producing precisely the current integer JSON token for integral eqops; do not serialize `4` as `4.0`. Old integer plan inputs should therefore re-hash identically. Fractional plans naturally receive a new fingerprint from the fractional canonical token. Preserve the current canonical payload key set unless a sidecar/schema version is chosen.
4. Avoid treating `long double` serialization as cross-platform exact. `nlohmann::json` stores floating numbers as `double`, and `long double` width/rounding varies by target. A compiler-generated cost computed in extended precision can round to different doubles on x86 (80-bit) and platforms where `long double == double`, changing plan hashes. Prefer a defined canonical rounding point based on the profile's `double` κ, then store/use that canonical double in Plan; use `long double` only for subsequent served accumulation. If design requires preserving more precision than binary64, use an explicit canonical decimal/fixed representation and version it; do not imply generic long-double JSON is exact. Also guard values above 2^53 if consumers expect exact JSON numbers: integral `uint64` is safe as an integer token, but converting a fractional value of that magnitude to `double` loses low bits.
5. Existing counters already expose both numeric and decimal-string forms. Keep them aligned: serialize whole eqops as integer where the contract requires it, and emit fractional numeric/decimal exact fields from the same canonical planned value. For fixed C ABI v2 integer members, never round fractional totals; leave ABI v2 unchanged and add a v3 scalar/JSON exact field only if those fixed structs need to carry arbitrary fractional plans.

## Conservation and focused regression coverage

Do not use `ceil(κ)` as a conservation fix: that changes the modeled charge. Define the canonical per-activity eqops value once, derive plan summary `vec_equivalent_ops` from the scheduled activities (or sum the same canonicalized tile/activity values), and have runtime served totals consume those exact planned values. Compare fractional served amounts against `planned × progress` under the existing numeric tolerance; retain exact integer equality for default integer profiles. Tests should include: integer κ preserving old plan JSON/fingerprint; fractional κ reflected identically in budget and activity/summary totals; strict-FP32 output INT4 charging `κ_quant`; plan v2 old-integer import/hash round trip; fractional plan serialization/import/hash round trip; runtime partial-progress and snapshot export/import preserving fractional counters; byte fields still reject floats; and C ABI v2 layout/ABI version unchanged. If a future fixed-layout v2 path accepts a fractional plan, explicitly reject it rather than truncate.

## Limits

This is a source-path/design audit, not a numerical precision proof or implementation. It does not claim fractional κ or compiled macro allocation accuracy has passed. Current strict-FP32 output INT4 uses cost 1 in the ledger and budget; joint conversion-cost repair is still required.
