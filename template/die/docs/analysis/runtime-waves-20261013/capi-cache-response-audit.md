# C API compile-cache response path: read-only audit

## Findings

The existing cache hit avoids `compile()`, but it does not cache the response representation. `cached()` still parses the request upstream, serializes each task with `task.dump()`, concatenates the hardware fingerprint and task JSON, and hashes that key on every lookup ([Capi.cc](../../../../die/src/Capi.cc#L102)). A hit only returns the retained `Plan` and updates LRU recency ([Capi.cc](../../../../die/src/Capi.cc#L104)).

For `compile_batch`, every successful result deep-copies `p->summary` into a new `json` tree, then the outer result path dumps that full tree to a temporary `std::string`, allocates a `malloc` buffer, and copies the bytes into it ([Capi.cc](../../../../die/src/Capi.cc#L76), [Capi.cc](../../../../die/src/Capi.cc#L119)). Fractional plans also add two result-level markers. Thus a cache hit still does JSON parsing, canonical task serialization and SHA-256, summary-tree copying, full response serialization, and a final response-buffer copy. The measured cache-hit p95 values were 34–42 μs (p50 32–40 μs); these cover the whole C ABI call, and static inspection cannot apportion the costs. **The dominant contributor is pending profile.**

The cache stores only the plan today. Its per-entry estimate is `retained_plan_bytes(*p) + key.size() + 512`; the 4,096-entry and 64 MiB bounds and LRU eviction use that value ([Capi.cc](../../../../die/src/Capi.cc#L107)). `retained_plan_bytes` accounts capacities in the plan’s JSON and containers, but it cannot account for response strings that do not yet exist ([Memory.hh](../../../../die/include/coarse_die/Memory.hh#L37)).

## Implementable response-template path

Profile first, then prototype a specialized serializer for `die_coarse_compile_batch_v2` while leaving `estimate_batch` and other C ABI results on the current `json` path. The proposal is internal to the existing v2 function; it adds no exported API and keeps `abi_mutex` held across lookup, handle registration, cache accounting, and output construction, as `result()` does now.

1. Add an immutable response template to each retained cache entry: at minimum a compact `summary_json` produced by `p->summary.dump()` once, and optionally the escaped `plan_hash_json` plus constant fractional marker state. Do not store a `plan_handle`; allocate a new ID and `PlanRef` for every successful compile-batch result, including cache hits and repeated tasks in one batch. `estimate_batch` uses the same cache today, so either populate templates on insertion for both call types, or add a correctly accounted lazy-template path when a compile-batch call first needs one. Eager creation is simpler and makes the first later compile hit predictable, but adds response-template memory to estimate-only cache entries.
2. Replace only the compile-batch result-tree path with a writer that emits the same JSON fields and values while appending the cached summary fragment as raw JSON. A first implementation can build one reserved `std::string` and pass it through a new `output(std::string_view)` overload; that still leaves one final copy into the C ABI `malloc` buffer but avoids a deep JSON summary copy and re-dumping its tree on each hit. If profiling shows that remaining copy matters, use a growable `malloc`/`realloc` writer and append directly into the returned buffer, keeping a trailing NUL and `free_result_v2` ownership unchanged.
3. Preserve the response contract exactly: top-level `schema_version`, `results`, `errors`, `cache_entries`, `cache_accounted_bytes`, and `cache_accounting`; positional sibling slots; result `plan_hash`, fresh numeric `plan_handle`, and object-valued `summary`; and the two result-level markers only when `has_fractional_work(*p)` is true. Leave summary values and JSON types as already formed by Mapping; in particular do not rebuild fractional counts through `double`. Keep the current `estimate_batch` shape unchanged.
4. Keep the current per-item exception boundary. A failed spec remains a null result with its positional error object (`status_code`, `reason`, and `field_path`); successful siblings survive. Top-level input/schema/serialization failures must still return null and set `last_error` through the existing structured-error path. Use JSON escaping for dynamic hash/error strings or the same nlohmann serializer rules; do not hand-escape strings.
5. Hold a `shared_ptr<const ResponseTemplate>` in any per-call row descriptor that refers to a template. Later specs in the same batch can insert entries and evict an earlier cache entry before the final response is written; a raw pointer into the map would then dangle. Keep per-entry templates immutable so LRU movement and concurrent handle release cannot mutate response bytes.

For a smaller first step, a `std::string` response builder with cached summary fragments is lower risk than a custom malloc writer and should already remove the large object-tree copy and repeated summary serialization. Use phase timings to decide whether to implement direct-to-malloc output or optimize task-key formation next. `task.dump()` plus concatenation/hash still runs on every hit; changing it requires preserving canonical equivalence for semantically identical JSON with different whitespace or object-key order, so using raw request bytes as a replacement key would change cache behavior.

## Retained-byte and eviction requirements

The cached summary/template is real retained allocation and must count against the existing limits. Include every new string’s `capacity() + 1`, not only its serialized `size()`, plus its object/control/allocator allowance. Use checked addition like `retained_plan_bytes`. Keep the existing 4,096-entry and 64 MiB eviction conditions and subtract the exact stored entry estimate on eviction. Do not exempt response strings, create a side cache outside the cap, or report plan-only bytes while retaining more memory.

When the template is stored as several strings, account each one. If the entry retains a separate plan hash or prefix/suffix fragments, include those capacities too. Preserve the plan/key/LRU costs already included in the current estimate. Recompute the report fields from the actual retained cache after processing the whole batch, as the current code does. Cache entries too large for the limit must remain uncached while the current call still returns its successful result and fresh handle.

This changes the numeric `cache_accounted_bytes` values and may evict earlier than the current plan-only estimate; its JSON key and numeric type stay the same. The docs currently say the count is not serialized JSON size ([implementation.md](../../../../die/docs/implementation.md#L133)). Once serialized fragments are retained and counted, update that wording to say it includes cached response fragments and remains a conservative retained-allocation estimate, not RSS. No ABI or JSON schema version bump is needed.

## Main risks

- **Handle leaks on writer failure:** the current batch registers handles before the outer JSON dump/output allocation. A failed serializer can return null after handles were inserted but before the caller receives them. A new writer must not worsen this; preferably stage pending handles and commit them only after the output buffer is successfully formed, rolling back any partial map insertion on failure. The IDs can remain monotonic and consumed.
- **Eviction and template lifetime:** do not retain map-entry addresses across later batch items; an insertion can evict them. A per-call shared template reference makes this safe, while cache accounting covers only the persistent cache ownership.
- **Per-sibling behavior:** moving to one top-level writer can accidentally turn an isolated compile error into a whole-batch failure or reorder `results`/`errors`. Keep the catch boundary around each task and test malformed siblings among successful tasks.
- **Serialization parity:** nlohmann currently emits integral fields as integers, fractional summary fields with their established JSON types, and escapes dynamic strings. Raw cached fragments must be valid UTF-8 JSON and must be generated from the exact retained summary. Preserve the v2/integer response without markers and the fractional result markers without changing summary contents.
- **Accounting and eviction shifts:** accounting `capacity()` rather than `size()` may reduce cache residency. Test both the entry-count and byte-count eviction boundaries, recency movement, oversize non-retention, and release of handles whose plans outlive cache eviction.
- **Scope of optimization:** a retained summary string addresses JSON-tree copying and repeated serialization, but request parsing, canonical task dump/hash, response assembly, and final allocation remain. The 32–42 μs result alone does not prove this is the dominant cost.

## Focused regression tests required before landing

- Compare parsed v2 compile-batch responses before/after for an integer plan and a fractional plan: all top-level/result/summary keys, JSON types, hashes, values, markers, and positional nulls match. Verify integer results omit both fractional markers and fractional results preserve both result-level markers and the summary sidecar.
- Extend the mixed-sibling C ABI case in [compile_execution_test.cc](../../../../die/tests/compile_execution_test.cc#L40): include a repeated valid task around one invalid task; require positional errors, unchanged reason/status/field-path behavior, distinct fresh handles for both successes, matching plan hashes, and successful release of every handle.
- Exercise a cache hit after a cache entry was first populated through `estimate_batch`, if templates are created lazily; ensure the first compile result still has the normal response and the cache byte counter includes any template added.
- Add focused cache-accounting tests that reserve extra capacity in each retained response string and prove accounting follows `capacity()`, with checked overflow. Exercise LRU hit promotion, the 4,096-entry limit, the 64 MiB byte limit, oversize plans that compile but are not retained, and `cache_entries`/`cache_accounted_bytes` values after eviction.
- Evict a cache entry while its returned plan handle remains live; verify that handle can still be used and released, and that an uncached subsequent request receives another fresh handle. Also test writer-allocation failure/rollback if the direct C-buffer writer is used.
- Preserve the existing fractional C ABI assertions in [fractional_work_test.cc](../../../../die/tests/fractional_work_test.cc#L44), including numeric `4.5`, `coarse_die_plan_v3`, and `dyadic_equivalent_work_v1` markers.

This is static inspection only. No production files were changed and no load/performance tests were run for this task.
