# die/ — Codex Cloud 跨账号开发及交接规则

本文件适用于仓库 `die/` 子目录。两个 ChatGPT Plus 账号分别运行独立 Codex Cloud 任务；
**GitHub 上已合入共享分支的代码与 docs/HANDOFF.md 才是共享状态**。
请勿假设能够读取另一个账号的聊天记录、隐藏 Session 状态或尚未提交的文件。

## 每轮任务开始前（必须）

1. 阅读 `die/docs/PROJECT.md` 与 `die/docs/HANDOFF.md`。
2. 检查当前分支、`git status`、`git rev-parse HEAD`、近期提交与工作区改动。
3. 如工具/权限允许，核实 GitHub 共享集成分支上的最新 commit SHA；确认工作区包含上次**已合并**的交付版本。
4. 如果分支/版本不一致、存在无法解释的未提交修改，或不能确认上轮改动已进入共享分支，先报告并停止有风险的修改，不能强行覆盖或猜测状态。
5. 先依据 `HANDOFF.md` 的 Next Step 继续，不重复已完成并通过验证的工作。

## 实施范围和开发节奏

### 当前硬件依据（2026-10-16，用户更新）

- 硬件权威文档为根目录[《架构建模_单Core版_严格复核修订.docx》](../架构建模_单Core版_严格复核修订.docx)，source_revision=`41f119135fd2d4cc87292f59b4b00adc918eece0`。当前只称 Core，由 SRAM/NoC 选择资源行，不提供类型选择；`architecture.core_type` 任意值都必须拒绝，不默认、不映射、不忽略。资源表为 `configs/core32.json`，id=`core32_v1`，共4档NoC×8档SRAM的32行，Core边长只取SRAM长边 `L0=a`。
- DOCX负责硬件几何/资源及用户给定的阵列；仿真路线与验收继续遵守根《die内仿真器设计文档_最粗粒度参数响应版.md》§1.5/§1.6/§8.2.1/§13。DOCX不含这些仿真合同，更新硬件不能撤销解析主线、10%/有据20%规则或速度预算。
- 历史源码、测试、raw、旧硬件身份与快照保留其原始范围，不篡改为当前Core设计的通过证据；不得恢复被移除的硬件类型、公式或类型字段。五仓固定SDK须在新公共模型验证后再同步，不能只改指纹就宣称迁移完成。

### 当前强制建模方法（2026-10-15，用户确认）

- **最新用户范围/精度（2026-10-15）**：输入用户指定的Die宽高/面积、Nx×Ny Core网格及其它硬件/任务配置，输出延迟。删除面积/Core排列/Core-first/Wafer-first/Pareto硬件搜索；不自动改硬件，Wafer不是当前必填范围。保留给定硬件下的软件分块/驻留映射及合法性派生。精度目标10%，多次有记录的合理测试/校准仍难达到时20%以内可接受，明确披露目标未达及适用范围；>20%失败。此决定替代旧3%/5%硬门槛，历史结果不改写。先同步设计文档到GitHub，再改代码。

- 生产主线为**解析工作量 + 固定数量的分段累计服务曲线 + 稳定区间直接积分**。循环/分块用于解析计数与容量检查，重复次数只进入公式；不逐 Core/tile/K/wave 推进内部执行。
- **周期搜索、精确周期/相位返回证明、大整数周期求解、逐 K 回放均不进入生产方案或接续主线。** 既有 Program/Cursor/周期研究仅按其适用范围复用计数或离线小规模验证，不以“状态固定”“先 opt-in”“以后再压缩”为理由恢复逐 K Program 路线；有效归档不删除。
- 服务曲线由实际循环、shape/精度/TP/span和工作量解析生成。有K累加时输入以统一 K 消费单位计数，输出以统一输出块单位计数；其他模板使用自身解析消费单位；首输出门槛是累计工作进度门槛，非固定时间；不得拟合曲线贴合参考。静态 SRAM 字节峰值与流体 credit 各自负责，不混用单位。
- 缓冲触边后施加切向速率约束并连续推进，禁止“满→停→空→启动”的逐块事件轮换。所有曲线折点/活动切换统一计入每 primitive 最多5、必要时8/16段的描述预算；固定外部事件序列和活跃规模后，Core/tile/K/repeat放大不能使内部状态或事件数线性增长。唯一显式例外(2026-10-17,用户授权"按你认为正确的方法做")：声明式生成repeat构造(plan schema v5顶层repeat块,任务显式声明repeat_seams)由运行时逐实例物化,其内部事件数与活动状态按O(count)增长(count<=kMaxPlanRepeatCount=4096),是该构造写入合同的明码代价;未声明该构造的遗留xR折叠描述仍完全受上述线性增长约束。
- 保留 owner 分组、Q/alpha、13域容量、PRIVATE 和每owner最多三个活动；解析/水填充快路径必须与原分配定义等价。保留真实网络、KV、迁移/恢复、ACK源释放和外部完成依赖。
- 从第一版同时验收速度和精度：缓存命中P95≤20μs、常规冷编译P95≤2ms、J≤32单次仲裁更新P95≤50μs（五仓CPU≤10%端到端预算已按2026-10-18维护者裁决删除）；轻量查询/规范化缓存同步推进。精度执行上方10%目标/有记录的20%容许范围；busy定义不变，补报绝对误差、参考共享时长和覆盖范围。正确性/守恒及速度门槛不放宽；未通过如实标failed或tradeoff_unresolved，不自行扩大误差容许范围。
- 完整合同见根设计文档§1.5/§8.2.1/§13及 `docs/PROJECT.md`、`docs/HANDOFF.md` 的最新路线；其后的历史恢复/周期建议不再作为当前Next Step。只使用活动 `astra-sim-joint`，已从main移除的 `_old` 不恢复。

- 用户新增的建模原则（2026-10-14）：与硬件设计参数、软件任务输入参数不直接相关的辅助细节，能用简单数学公式直接计算时，采用公式，不进行深入建模。
- 复杂度须服务于可观察的参数响应、容量/工作量守恒或外部依赖与竞争。优先闭式、解析计数和固定数量的分段公式；新增状态或复杂数值机制须说明关联的输入/行为、简单公式不足的证据及运行成本。
- 该原则不能用来省略源架构变量、真实任务 shape/精度/TP/span、必要的就绪和共享资源约束，也不能通过额外延迟系数人为制造参数响应。

- 优先只修改 `die/`；其他目录如需变更，先说明必要性与风险。
- 读取真实代码再规划工作；不要猜测项目功能、入口、测试命令或用户意图。
- 把长任务分为小而完整、可以验证的阶段；每完成一个阶段尽可能形成可提交的成果。
- 遵守已有设计决策，并及时在 `PROJECT.md` 或 `HANDOFF.md` 记录新决策。
- 不允许两个独立 Session 同时修改同一套文件或向同一共享分支并行推送冲突内容。
- 不要提交 API Key、访问令牌、凭据、个人隐私、临时缓存或大型生成产物。

## 每轮结束/换账号前（必须）

1. 运行相关测试，忠实记录命令和结果；不能运行时说明原因，**不得声称未执行的测试已通过**。
2. 更新 `die/docs/HANDOFF.md`：Current Status、Completed、Next Step、Important Decisions、Files to Continue、Tests、Blocking Issues、Handoff Notes。
3. 清楚记录尚未完成的工作、关键判断以及接手方必须知道但难以从代码推出的信息。
4. 尽可能把代码改动和 HANDOFF.md 一起提交。允许操作时推送或创建 PR；无权限时，列出用户需要在 Codex Cloud / GitHub 界面完成的具体步骤。
5. **PR 未合并、推送失败、测试阻塞或远端版本未确认时，明确标记 NOT READY FOR HANDOFF**，不能宣称下个账号可直接接棒。
6. 最终答复包括：工作分支、提交 SHA（如有）、PR 链接和合并状态、测试结果、下一步。

## 交接判定

只有当上一轮成果进入 `PROJECT.md` 指定的共享集成分支，并且 `HANDOFF.md` 与代码一致时，
下一账号才应基于最新 GitHub 状态创建新 Cloud Task 接棒。

此协议只实现**代码与摘要状态接力**，不提供跨账号 Session 恢复，不检测额度，也不自动切换账号。
